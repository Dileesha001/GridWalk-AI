# Member 2 Step 5: Auditor and event polling handoff

`run_triage(fault_id)` remains the entry point. Its `TriageResult` now carries a UUID `run_id` and a typed `recovery_result: RecoveryResult`. The existing `status`, before/after `GraphState`, attempts, and validation evidence remain available. The public call uses `ExecutionMode.PRIMARY_AI` only when a plan is committed; an uncommitted or duplicate run uses `NONE`. Backup and deterministic modes are reserved for Step 6.

`get_agent_events(run_id: str = "") -> list[AgentEvent]` is a polling read. Pass the returned `run_id` to read exactly one run, including after a reset. Omitting it reads the latest completed run for the current grid generation; a reset makes that default view empty until another run completes. Unknown IDs return an empty list. `get_recovery_result(run_id: str) -> RecoveryResult | None` reads the same stored result. The Jac server exposes these functions from the `main.jac` import; Member 3's adapter should use the typed return values and handle the standard Jac response envelope. There is no streaming or in-progress polling in Step 5: events are stored together when `run_triage` returns.

`AgentEvent.sequence` starts at 1 for each run and follows observation → proposal → validation/rejection → optional revision → application → audit, or a final no-action/failure event. Every event has the same `run_id`. A proposal explicitly says its actions are **not applied**. An application event exists only after Member 1's `apply_approved_plan` returns a committed `GraphState`; its evidence names only those committed actions. No fallback event is emitted before an actual Step 6 fallback attempt. A validator acceptance is evidence about a candidate, not a commit.

The `IncidentAuditor` walker checks accepted validation evidence and the returned committed state. Applied actions are projected from changes visible between the before and after graph states. Its summary is generated by Jac from the observed fault, committed actions, and authoritative metrics. It does not claim the physical fault was repaired. If the walker fails after application, orchestration retains the valid recovery, emits an audit fallback event, and returns the same factual Jac summary. AI-written audit prose is not enabled in this step, so there is no extra provider call after commit.

`RecoveryResult` contains `outcome`, `execution_mode`, `applied_actions`, before/after `GridMetrics`, `incident_summary`, proposal/revision counts, elapsed milliseconds, and an optional failure reason. `recovered` means no unmet demand remains; `partial` means a valid applied plan preserves critical demand but leaves some demand unmet; `infeasible` is used when final computed critical preservation is below 100%; `failed` means no plan was applied for another reason; `no_action` means a duplicate request committed nothing. The exact graph state remains in `TriageResult.after_state`.

The event records are nodes under the caller's Jac root rather than process globals. Member 3 should retain the returned `run_id` and discard older asynchronous responses in the client. Request limits, concurrent-run control, backup providers, and deterministic fallback remain Step 6 work. Jac 0.34.13 compiled all changed Step 5 files; runtime event persistence and client integration are still to be checked.
