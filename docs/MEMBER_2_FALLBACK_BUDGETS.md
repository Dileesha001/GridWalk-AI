# Member 2 Step 6: provider budgets and deterministic handoff

The current public `run_triage(fault_id)` calls the primary Gemini Planner first. It allows at most two proposals, including one validator-feedback revision. If that phase fails at the provider or exhausts proposals without a commit, it switches once to Groq when enough time remains for a provider call. If AI planning does not commit a plan, it tries Member 1's deterministic candidate generator before the run deadline. The orchestration checks the current grid snapshot, validates every candidate, and applies only an approved plan. The final `RecoveryResult.execution_mode` is `primary_ai`, `backup_ai`, or `deterministic` only when that mode's plan actually commits; otherwise it is `none`. Event records identify proposal modes and each fallback transition.

Provider settings are together in `agents/planner.jac`: primary `gemini/gemini-3.8-flash`, backup `groq/openai/gpt-oss-120b`, and a 15-second ModelPool request timeout. Each one-model pool has `num_retries=0`; each typed call has `max_output_retries=0`. The orchestration permits two calls per provider and one provider switch, with a 65-second run deadline. It checks the remaining time before another provider call and again before validation/application. A received proposal cannot be applied after the deadline. The timeout is the adapter's request limit; the total wall-clock limit still depends on the adapter honoring that timeout. Unknown provider errors are not copied into the result or events.

The ignored `.env` may contain `GOOGLE_API_KEY` and `GROQ_API_KEY`; no key belongs in source, logs, or the client. Groq's model catalog lists `openai/gpt-oss-120b`; LiteLLM uses the `groq/` prefix for Groq model routing. The local Groq key was exercised on Jac 0.34.13 under WSL on 2026-10-17. `scripts/step06_groq_smoke.jac` returned a typed `CLOSE_SWITCH SW-TIE-B-H` plan for `FAULT-LINE-A-H`; the validator accepted it, and the graph revision remained 1 because that script does not apply plans. `scripts/step06_backup_run_smoke.jac` then used a labeled fixed primary failure and the live Groq backup through the normal provider-routing code. One Groq proposal was accepted and applied. The stored result reported `backup_ai`, `partial`, one fallback event, revision 1→2, critical preservation 100%, and served demand 145→135 kW after `LOAD-OFFICE` was shed. The physical line fault remained active. These are observations from one run, not a guarantee that later stochastic proposals will be accepted. See [Groq supported models](https://console.groq.com/docs/models), [Groq model deprecations](https://console.groq.com/docs/deprecations), and [Jac byLLM ModelPool and retries](https://docs.jaseci.org/reference/plugins/byllm/).

**Member 1 handoff received:** `grid/fallback.jac` now exports `deterministic_fallback_plan(observed: GraphState) -> RecoveryPlan | None`; `generate_fallback_plan` remains a compatibility wrapper. Member 2's Step 7 orchestration calls the canonical function when AI planning has not committed a plan and time remains, checks the current generation and revision, then passes any candidate through `validate_plan` and `apply_approved_plan`. A `None` result commits nothing and leaves the faulted state visible. The function's internal proposal search is not an application or an authority to bypass the validator.
